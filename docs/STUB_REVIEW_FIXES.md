# POZ-7045 — исправления внешнего ревью, R2

**Историческая итерация R2. Ревьювер подтвердил закрытие замечаний R1, но выявил
ещё открытые служебные маршруты. Актуальные исправления и проверки —
[STUB_REVIEW_R3.md](STUB_REVIEW_R3.md).** Лимит входа по email из этого отчёта
также снят в R3; контакт ReferralInfoRules унифицирован.

11.11.2026. Актуальный отчёт для повторного независимого ревью.
Предыдущий `STUB_REVIEW_REPORT.md` сохранён как исторический R1 и помечен
отклонённым внешним ревью. Ниже описаны исправления именно замечаний ревьювера.
Повторного внешнего одобрения пока нет. Коммит, push, SSH и серверные изменения
не выполнялись; рабочий стейдж `parsec_db`/`parsec_redis` не пересоздавался.

## Блокеры и решения

| Замечание | Исправление | Проверка |
| --- | --- | --- |
| IDOR: доступ к чужим users/:id и ротации ключа | users.controller.ts удалён вместе с регистрацией в UsersModule. Удалены также общий POST /users и PATCH. Собственные /users/me и защищённые admin-маршруты оставлены | Свежая учётка получает 404 на GET/PATCH/rotate/POST; имя, роль, баланс и hash ключа отдельной тестовой жертвы не изменились; /users/me/balance работает |
| Поддельный webhook пополняет баланс | PaymentService.processWebhook при STUB_MODE возвращается до чтения payload и до любых обращений к БД/биллингу/чекам. Из controller убрано логирование тела callback | На обоих notify/callback HTTP 200 для поддельного запроса с существующим синтетическим NEW PaymentId и для пустого объекта; платёж, все балансы и число проводок неизменны. Unit-тесты дополнительно проверяют null и нулевые вызовы зависимостей |
| Частоты списывают деньги без обработчика | FrequencyService.createTask при STUB_MODE сразу возвращает makeError(SERVICE_UNAVAILABLE=52), до валидации/биллинга/очереди | С действительным ключом нового пользователя status:error/code:52; все балансы, число проводок и частотных задач неизменны. Unit-тест подтверждает отсутствие вызовов репозиториев, transaction, charge и KeyTurbo |
| Timescale tune использует RAM общего хоста | В compose заданы mem_limit, cpus, TS_TUNE_MEMORY/NUM_CPUS/MAX_CONNS; переменные есть в примере env | Новый тестовый контейнер: shared_buffers 128MB, effective_cache_size 384MB, work_mem 3413kB, max_connections 60; HostConfig.Memory=1073741824, NanoCpus=1000000000 |
| Разные контакты | Nick подтвердил @parsec_help. Один shared/config/support.ts используется заглушкой, плавающей кнопкой и BalanceModal | В финальном Docker HTML лендинга и dashboard есть t.me/parsec_help, старого t.me/toolzar_help нет |

Создание частот — **осознанное уточнение исходного требования о неизменности
публичного API**: во время заглушки нельзя списывать деньги за задачи без
обработчика. Файлы `modules/public-api` побайтово не изменены; изменён вход
FrequencyService и добавлен код 52 в frequency.errors.ts. Возвращается прежний
JSON-формат ошибки. Контроллер сохраняет свой прежний HTTP 201 даже для
возвращаемых ошибок; фактически проверен `201 + {status:'error', code:52, …}`.
Не выдавать это за HTTP 503. В обычном режиме этот guard не меняет создание.

Снятие STUB_MODE **запрещено до отдельного исправления банковской подписи**:
старый webhook-код вне заглушки по-прежнему небезопасен. Перед восстановлением
нужны подпись, проверка сохранённого order/user/amount и идемпотентность. Это
явно добавлено в памятку следующему агенту; одной 503 на создании платежа мало.

## Остальные замечания

- BalanceModal теперь содержит только актуальное сообщение обслуживания и
  контакт. Нет «закрывается 15.08», false && и скрытой платёжной формы.
  Оплата остаётся отключённой независимо от флага кабинета; памятка описывает
  отдельное восстановление этой UI-ветви вместе с backend-платежами.
- Добавлен `infra/nginx/klaster-key-parsec-https.conf`. HTTP и HTTPS применяются
  отдельными cat >>; вручную вырезать 443-блоки не требуется. Их сумма равна
  полному reference-конфигу, генератор проверяет это перед созданием патча.
  В инструкции и генераторе одинаковый разделитель: два LF перед первым
  фрагментом. Проверка git apply --check/apply для LF, CRLF и отсутствующего
  завершающего LF подтвердила точное равенство реальному append.
- Всё тело deploy.sh помещено в функцию, которая разбирается Bash до git pull.
  Тест подменял выполняемый файл на `exit 99` во время mock pull: исходная
  функция всё равно завершила HBA, build, up --no-deps и ps. Ни git, ни Docker
  в этом тесте не выполняли настоящих изменений.
- Redis в production не публикует host-порт. Для отдельного npm-стейджа добавлен
  `docker-compose.local.yml` с bind 127.0.0.1 и LOCAL_REDIS_PORT. Production
  использует только основной compose, в README команды разделены.
- Auth защищён существующим @nestjs/throttler на register/login/forgot/reset.
  Ограничения действуют и вне заглушки, не затрагивают публичное API и /auth/me.
  Помимо IP есть отдельный нормализованный ключ email, поэтому смена IP и
  регистра символов не обходит ограничение сброса.
- В AppModule один ConfigService и один scheduleEnabled для всех Schedule-опций.
  Env по-прежнему загружается до вычисления флага; защита от startup race сохранена.

## Auth limits

| Метод | IP | Учётка (нормализованный email) |
| --- | --- | --- |
| register | 5/мин | 30/час |
| login | 10/мин | 30/час |
| forgot-password | 3/мин | 3/час |
| reset-password | 10/мин | 30/час по IP, поскольку email в этом DTO нет |

Лимиты раздельные для методов. Нормализация email: trim, lower-case, ограничение
длины; тип входа проверяется до обращения к строковым методам, поскольку guard
работает раньше DTO validation. Для одного backend-процесса используется
in-memory storage библиотеки; рестарт сбрасывает окна. При нескольких репликах
потребуется общая реализация storage. Доступ к backend извне должен идти только
через ожидаемый nginx: сохраняется trust proxy=1; серверные сетевые проверки впереди.

## Ресурсы и существующие тома

Defaults: DB_MEMORY_LIMIT=1g, DB_CPU_LIMIT=1.0, TS_TUNE_MEMORY=512MB,
TS_TUNE_NUM_CPUS=1, TS_TUNE_MAX_CONNS=60. Итоговые параметры compose проверены
без вывода секретов. 60 соединений оставляют запас поверх backend pool max=40.

На сервере сначала проверить свободные ресурсы и согласовать окончательный
бюджет. Tune применяется только при первой инициализации пустого тома. На уже
записанном postgresql.conf эти env ничего не поменяют: нельзя просто уменьшить
mem_limit под старую настройку shared_buffers в несколько гигабайт. Проверить
SHOW и изменить конфиг отдельно. Это явно внесено в infra/README.md.
Рабочий стейдж и восстановленная проверочная БД не перетюнивались этим тестом.

## Границы результата и следующий шаг

Исправления готовы для повторного внешнего ревью; это не самостоятельное
подтверждение, что оно пройдено. Дальше — замечания ревьювера, затем быстрый
ручной тест Nick. Визуальная UI-автоматизация по-прежнему недоступна в сессии.
На сервере пока не проверены внешняя HBA-фильтрация, bind gateway, nginx -t,
сертификаты и неизменность чужих production-сервисов: соединений с сервером нет.
Все эти действия остаются отдельным этапом только по команде Nick.
