# POZ-7045 — исправления после повторного ревью, R3

После одобрения R3 выполнена отдельная lint-only задача Nick:
[LINT_AND_VSCODE.md](LINT_AND_VSCODE.md). Все прежние lint-ошибки устранены;
побайтовые сравнения ниже описывают состояние ДО этой задачи. Runtime публичного
API сохранён, его type-only изменения проверены сравнением AST сгенерированного JS.

11.11.2026. Отчёт для следующего независимого ревью. Ревьювер подтвердил все
исправления R1/R2, но нашёл открытые служебные маршруты и неограниченный SMTP
import-request. Здесь зафиксировано их закрытие. **Внешнее ревью R3 пройдено:
блокирующих коммит замечаний не осталось (подтверждено Nick 11.11.2026).**
Следующий этап — ручной тест Nick, затем отдельные команды на коммит и сервер.
Коммитов, push, SSH и серверных действий не было; рабочий стейдж не менялся.

## Что исправлено

### Общая авторизация администратора

Добавлен `common/guards/admin.guard.ts`, экспортируется из AuthModule.
Гард вызывает существующий JwtCookieGuard, который проверяет JWT-cookie и
загружает пользователя из БД. Затем допускается только массив ролей с точным
значением admin. Отсутствующая/некорректная сессия и удалённый пользователь —
401; обычная роль, support и строка superadmin вместо массива — не допускаются.

Гард действует независимо от STUB_MODE. Поставлен на классы контроллеров,
чтобы автоматически защищать и чтение, и все их изменяющие/тяжёлые методы:

| Контур | Обработчиков | Защита |
| --- | ---: | --- |
| /admin/economy/* | 4 | AdminGuard на EconomyController |
| /api/v1/admin/throughput, rebuild, DELETE | 3 | AdminGuard на TaskThroughputController |
| /task-stats/recalculate-stats | 1 | AdminGuard на TaskStatsController |
| /admin/test-bench/config/* | 5 | AdminGuard на TestBenchEngineConfigController |
| /admin/test-bench/phrases/* | 5 | AdminGuard на TestBenchPhrasesAdminController |
| /api/v1/admin/testbench/* | 11 | AdminGuard на TestBenchController |
| /referral/generate-codes | 1 | AdminGuard только на этом методе |

В EconomyModule, TaskStatsModule и TestBenchModule добавлен импорт AuthModule
для DI. ReferralModule уже импортировал его. Публичная проверка referral-кода
оставлена доступной для регистрации, собственные referral-данные сохраняют JWT-защиту.

### Защита SMTP

`POST /mail/import-request` остаётся публичной формой заявки, с тем же
ThrottlerGuard и общим AUTH_RATE_LIMITS, что использует auth. Для маршрута:

- 3 запроса в минуту с IP;
- 10 запросов в час суммарно на ящик получателя, независимо от IP и contact.

Для общего лимита переопределён tracker на константу import-mailbox. Ключи
библиотеки дополнительно включают controller/handler, поэтому исчерпание
import-request не блокирует отправку сброса пароля. Guard выполняется перед
вызовом MailService: заблокированный запрос не отправляет письмо.

Storage пока in-memory одного backend-процесса, как в R2; рестарт сбрасывает
окна, несколько реплик потребуют общей реализации storage. Добавления новых
пакетов и самостоятельной реализации throttling не было.

### Неблокирующие замечания

- Для login отключён account-throttler через SkipThrottle({account:true}).
  Остаётся 10/IP в минуту; посторонний больше не может закрыть чужую учётку
  через исчерпание общего email-счётчика. Forgot-password сохраняет оба лимита.
- В AUTH_RATE_LIMITS задан русский текст: «Слишком много запросов. Попробуйте
  позже.». Реальный HTTP 429 проверен, английского ThrottlerException в message
  нет. Глобальный filter нормализует регистр; визуальный вид формы ещё относится
  к ручному тесту, браузерной автоматизации в сессии нет.
- ReferralInfoRules теперь берёт URL и handle из общего SUPPORT_CONTACT,
  `@parsec_help`. Поиск `toolzar_help` по всему parsecclient/src пустой.
- У MailController убран ненужный async, устранена его прежняя lint-ошибка.

## Регрессионные тесты

Добавлен `common/guards/admin.guard.spec.ts`: реальные контроллеры, AdminGuard
и JwtCookieGuard, подменены проверка JWT/пользователь и бизнес-сервисы. Для
каждого из 30 маршрутов проверены:

1. Без cookie — 401, ни один бизнес-сервис не вызван.
2. Обычный пользователь — 403, ни один бизнес-сервис не вызван.
3. Admin — обработчик доступен и вызывает соответствующий mock-сервис.

Ещё проверены некорректный token, удалённый пользователь, support, некорректный
тип role и сохранение публичной referral-validation. Эти тесты не выполняют
пересчётов, удалений, HTTP к парсерам или записей в реальную БД.

`mail-rate-limit.spec.ts` проверяет пороги IP и общего ящика, число вызовов
MailService и русский 429. В auth-rate-limit.spec.ts добавлены 31 вход с одним
email и разными IP без блокировки учётки, а также сохранение IP-лимита.

**Итог: 6 suites, 119 тестов — PASS.** Ранее было 20 тестов; прирост главным
образом составляет матрица 30 маршрутов × 3 режима доступа.

## Проверка настоящих Docker-образов на копии дампа

Оба образа пересобраны; обновлены только parsec-stub-review-back/web.
Проверено через HTTP с настоящим JWT и пользователями проверочной БД:

- Все 30 обработчиков: 401 анониму, 403 новому обычному пользователю.
- Некорректная cookie — 401. Настоящий admin с ролью из БД читает
  /admin/economy/registrations с 200. Изменяющие методы с admin-cookie в живой
  БД **не запускались**; положительные проверки записи выполнены на mocks.
- Публичная referral-validation остаётся 200.
- 31 неверный пароль для одной новой учётки с разных IP возвращает 401,
  следующий корректный вход этой учётки проходит; email-lockout отсутствует.
- Сброс для одной учётки: три запроса проходят, четвёртый с другого IP — 429
  с русским message.
- Import-request: четвёртый запрос с IP — 429; после десяти принятых заявок
  со всех тестовых IP следующий с нового IP — 429. Forgot-password при этом
  проходит со своим отдельным счётчиком.

Перед проверкой mail подтверждено, что NODE_OPTIONS загружает SMTP-preloader
и Nodemailer перехвачен. Все письма записывались локально, живой SMTP и ящик
Семёна этим прогоном не использовались. Генерация admin-JWT происходила только
для изолированного loopback-стенда, с его тестовым секретом; токен не выводился
и не сохранялся в Git. В проверочную копию добавлены только одноразовые учётки.

Повторены прежние сценарии R1/R2: IDOR 404, поддельные webhook без начисления,
частоты code:52 без списания, регистрация/referral/дубликат email, вход новой и
старой учёткой, cookie, logout, полный сброс с локальным перехватом письма,
payment/create 503, десять защищённых страниц и редиректы payment. Все PASS.
Старый пароль и баланс тестовой учётки Nick не менялись.

Финальный backend наблюдался 13:02:14–13:05:59 по времени Nick (более трёх минут).
Маркер STUB_MODE со счётчиками 0/0/0 присутствует; фоновых запусков и seeder
в логах нет. Рабочие parsec_db/parsec_redis сохранили прежние CreatedAt.

Временный HTTP-harness: ignored `tmp/r3-access-check.cjs`.
