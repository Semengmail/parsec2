# Памятка агенту: заглушка и восстановление боевого функционала

Дата: 11.11.2026. Задача POZ-7045. Рабочий репозиторий — parsec2, не старый monorepo.
Сначала прочитать этот файл и `infra/README.md`. Здесь зафиксирован намеренный
объём заглушки; не переписывать авторизацию и публичное API ради её снятия.
Production-действия, коммиты и push — только по отдельной команде Nick.

## Что сейчас работает

Лендинг, регистрация `/register`, вход старых и новых пользователей, выход,
реферальный код при регистрации, сброс пароля через SMTP. Кнопки лендинга ведут
на `/register` того же домена: отдельной формы на главной не требуется.
Пользователи и баланс берутся из восстановленной старой БД. Пароли не
перехешировывались, алгоритм bcrypt и авторизация не заменялись.
Куки по-прежнему `psk.sid` на `.toolzar.ru`, HttpOnly; исходный API_KEY_ENC_SECRET
нужен для расшифровки старых API-ключей, не менять его случайным новым значением.
После внешнего ревью внесены дополнительные защитные изменения: актуальный
отчёт — `STUB_REVIEW_R3.md`. STUB_REVIEW_FIXES.md описывает исправления R2.
Старый STUB_REVIEW_REPORT.md описывает первую
итерацию, которую ревьювер отклонил до устранения блокеров.

## Два независимых флага

| Флаг | Где задаётся | Действие | Как применить |
| --- | --- | --- | --- |
| STUB_MODE | backend env / infra/.env | Отключает Schedule, seeder, Alerting/Telegram, обработку webhook и создание задач частот | Пересоздать только backend с нужным env |
| NEXT_PUBLIC_STUB_MODE | client env / infra/.env → build.args | Все защищённые страницы заменены заглушкой, редиректы входа фиксированы | Пересобрать и пересоздать frontend; runtime env недостаточно |

Оба флага должны быть true для заглушки и false для возврата обычного кабинета.
По умолчанию в коде они false, в production-примере infra — true.
Изменение только одного флага создаёт несогласованный режим.
**Не переключать STUB_MODE в false до исправления банковской подписи webhook:**
при false старая обработка снова включается, а она не проверяет подпись и
доверяет сумме/пользователю из запроса. Наличие 503 на создании платежа этого
не устраняет. Это обязательный отдельный этап восстановления, не предположение.

Воркер, запускающийся отдельно от Nest Schedule, при текущей проверке не найден.
В `modules/public-api` есть только type-only lint-правки, поведение не изменено:
workers были @Interval, cleanup — @Cron. Побайтовое совпадение исходников больше
не является инвариантом; сохраняется поведение публичного API относительно R3.
Остальные маршруты публичного API могут принимать задачи при заглушке,
но интервальные воркеры их не исполняют; синхронные запросы остаются прежними.
Исключение для создания частотных задач описано ниже. Не путать выключенный фон
с глобальной блокировкой всего API.

Уточнение после ревью: создание **частотных** задач через FrequencyService
теперь намеренно отклоняется, чтобы не списывать баланс при выключенном cron.
Ответ сохраняет форму `{status:'error', code:52, error:'…'}` и прежний HTTP-статус
контроллера (201). Файлы `modules/public-api` не менялись; остальные его
контракты не переделывались. Не удалять эту защиту до готовности обработчиков.

## Что флагами не возвращается

- Создание платежа — намеренная постоянная 503 до отдельной задачи. Callback и
  notify при STUB_MODE=true подтверждаются без обработки; status не переписывался.
  Перед STUB_MODE=false исправить небезопасную обработку webhook, затем проверить
  все ветви, подписи вебхуков, чеки, реквизиты, idempotency и тестовый платёж.
- CI deploy удалён. Используется ручной deploy.sh с --no-deps только для
  приложения; базу/Redis он не обновляет. Возвращать GitHub Actions не требуется.
- Nginx Proxy Manager, его тома и /files удалены из compose. Их НЕ возвращать:
  80/443 уже принадлежат nginx боевого klaster-key.
- Старые уведомления «сервис закрывается 15.08» НЕ возвращать.
- TYPEORM_SYNC=true с 12.11.2026 по решению Nick: при старте бэкенда TypeORM сам
  приводит схему к entities. Удаление или переименование поля/таблицы в entity
  удалит данные на проде при следующем старте — перед такой выкладкой снять
  pg_dump и проверить DDL на копии (infra/README.md, «Синхронизация схемы»).
- HBA allowlist, bind на gateway, точный TimescaleDB PG17, исключение секретов
  из Docker-сборки и обновления безопасности зависимостей тоже оставить.
- Лимиты БД оставить: по умолчанию контейнеру 1 GiB/1 CPU, tune 512MB/1 CPU,
  max_connections=60. На уже инициализированном томе env не переписывает
  postgresql.conf; проверить реальные SHOW-параметры до изменения лимитов.
- Redis в production не публикуется на хосте. Для npm-стейджа есть отдельный
  `infra/docker-compose.local.yml`, не добавлять этот override в серверный запуск.
- Auth throttling остаётся независимо от заглушки: login — только 10/IP в минуту,
  без лимита по email (защита от блокировки чужой учётки). Reset — 10/IP в минуту
  и 30/IP в час; register 5/IP в минуту и 30/учётку в час; forgot 3/IP в минуту и 3/учётку
  в час. Ключ учётки нормализует регистр/пробелы. Хранилище в памяти одного
  backend-процесса; при нескольких репликах нужна общая реализация storage.
  Текст 429 задан по-русски в AUTH_RATE_LIMITS и используется также для import-request.
- AdminGuard действует независимо от STUB_MODE. Он не отключает ручной запуск
  пересчётов для администратора: не вызывать их при smoke-тестах на реальных
  данных. selectors/report теперь тоже требует админскую сессию; если его
  вызывает бот, решать отдельную интеграционную авторизацию, не открывать маршрут.
- GET и POST /parser-heartbeat остались открытыми намеренно: это интеграция
  внешних парсеров. Не закрывать их без отдельного решения о протоколе доступа.
- Сохранять отдельные HTTP/HTTPS nginx-фрагменты и их точное объединение.
  Не вырезать блоки вручную: это расходится с патчем для klaster-key.

## Порядок восстановления

1. Отдельно подтвердить, какой функционал возвращается. Снять свежий бэкап
   и проверить его читаемость. На копии базы проверить совместимость схемы.
2. До включения STUB_MODE=false посмотреть очереди старых задач, cron, тарифы,
   test-bench и heartbeat: после запуска возобновятся запросы к Rankscan/KeyTurbo,
   расчёты, уведомления и обработка сохранённых очередей. Решение о старых
   pending-задачах принять явно; не удалять их и не начинать обработку вслепую.
3. Настроить интеграции и alert recipients на локальном/отдельном стейдже.
   Выключить оба флага, пересобрать клиент, проверить обычный кабинет.
4. Прогнать build/lint/test, вход старым пользователем, регистрацию с referral,
   сброс, выход, API и фон. Оплату включать отдельным изменением после проверки.
5. Провести независимое ревью, затем ручной тест Nick. Только по его команде
   коммит/push/production; там по-прежнему нельзя пересоздавать чужие контейнеры.
